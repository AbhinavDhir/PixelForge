# PixelForge — Prompt-Controlled Pixel Art Character Generator (Conditional DCGAN)

PixelForge trains a **conditional DCGAN from scratch** on the public **TinyHero** sprite dataset. Type a
description such as *"a front-facing hero with green hair and a red tunic"* and it generates **new 64×64 RGB
pixel-art RPG characters** that match it. It includes a standalone Google Colab notebook, command-line scripts,
an evaluation suite (including a measured **prompt-controllability** experiment), unit tests, and a
retro-styled Streamlit studio ("PIXELFORGE — AI RPG Character Studio").

**How a prompt reaches the GAN.** TinyHero has no captions, so every sprite is **labelled automatically**:
viewing direction (exact, from the dataset folders), hair/headwear colour and outfit colour (measured from the
pixels). A keyword parser turns a prompt into those labels $y$, and the conditional generator draws $G(z, y)$.
The model understands **direction, 9 hair colours and 9 outfit colours**. Other words (e.g. "wizard", "sword")
are ignored, because no labels exist for them.

No pretrained image generators, diffusion models or external generative APIs are used. Every "generated"
image comes from the generator trained in this project.

## 2. Problem statement

Game developers need large numbers of varied character sprites. Hand-drawing them is slow. The task is to
**learn the distribution of pixel-art RPG characters from examples** and then **sample new, plausible
characters** that are not copies of the training data. This is an unsupervised generative-modelling problem:
given samples $x \sim p_{data}$, learn a generator $G$ such that $G(z)$ with $z \sim \mathcal{N}(0, I)$ follows
$p_{data}$ as closely as possible.

## 3. Dataset information

**TinyHero** — https://github.com/AgaMiko/pixel_character_generator (`data.zip`, 7.3 MB).

Verified by `python dataset.py` (results in `outputs/dataset_stats.json`):

| Property | Verified value |
|---|---|
| Images | 3,648 PNG files |
| Characters | 912, each present in all 4 view folders (same file name = same character) |
| Folders | `0` = back, `1` = left, `2` = front, `3` = right (912 each) |
| Size | 64×64 for every file |
| Mode | **RGBA** for every file, binary alpha, ~76% of pixels fully transparent |
| Matches documentation | yes |

**Important preprocessing detail:** the sprites are RGBA, and the RGB values under transparent pixels are
black. PixelForge **alpha-composites each sprite onto an explicit solid background colour**
(`Config.background`, CLI `--background R G B`) before converting to RGB, then normalises with
$x' = x / 127.5 - 1 \in [-1, 1]$.

**Why black and not white?** White was the first choice, because dark outlines stay visible on it. But with
a white background the DCGAN **mode-collapsed in every configuration tried**: all 64 fixed latent vectors
produced the same sprite by epoch 5. With black, the same model stays diverse. See the
[experiment log](#experiment-log-mode-collapse-and-the-background-colour). Black is also what the original
TinyHero notebooks used. The trade-off: dark outlines blend into the background.
All 3,648 images are decoded once into a uint8 tensor in RAM (~45 MB).

All four directions are used by default (3,648 images). Training on front-facing sprites only
(`--views 2`) is supported but leaves just **912 images**, which makes GAN training noticeably harder
(fewer samples → discriminator overfits faster).

Outputs: `outputs/plots/dataset_samples.png` (25 random real images) and `outputs/plots/dataset_views.png`
(characters × 4 directions).

## 5. GAN architecture

```
           z ~ N(0, I)  (100-d)
                │
        ┌───────▼────────┐        fake 3×64×64
        │   GENERATOR    │ ─────────────────────┐
        └────────────────┘                      ▼
                ▲                       ┌───────────────┐
                │  ∇ through D          │ DISCRIMINATOR │ ──► logit (real / fake)
                └────────────────────── └───────────────┘
                                                ▲
         TinyHero sprite 3×64×64 ───────────────┘
```

Standard DCGAN (Radford et al., 2016): strided convolutions instead of pooling, BatchNorm, no fully
connected hidden layers, ReLU/Tanh in G, LeakyReLU in D, N(0, 0.02) initialisation.

## 6. Generator

```
z (100×1×1)
 → ConvTranspose2d(100→512, k4, s1, p0) + BN + ReLU   → 512×4×4
 → ConvTranspose2d(512→256, k4, s2, p1) + BN + ReLU   → 256×8×8
 → ConvTranspose2d(256→128, k4, s2, p1) + BN + ReLU   → 128×16×16
 → ConvTranspose2d(128→64,  k4, s2, p1) + BN + ReLU   → 64×32×32
 → ConvTranspose2d(64→3,    k4, s2, p1) + Tanh        → 3×64×64  in [-1, 1]
```

**3,576,704 parameters** (~14.3 MB in fp32). Each stride-2 transposed convolution exactly doubles the
spatial size: $(H-1)\cdot2 - 2\cdot1 + 4 = 2H$. Tanh matches the [-1, 1] range of the normalised data.

## 7. Discriminator

```
x (3×64×64)
 → Conv2d(3→64,    k4, s2, p1) + LeakyReLU(0.2)       → 64×32×32   (no BN on the input layer)
 → Conv2d(64→128,  k4, s2, p1) + BN + LeakyReLU(0.2)  → 128×16×16
 → Conv2d(128→256, k4, s2, p1) + BN + LeakyReLU(0.2)  → 256×8×8
 → Conv2d(256→512, k4, s2, p1) + BN + LeakyReLU(0.2)  → 512×4×4
 → Conv2d(512→1,   k4, s1, p0)                        → 1 raw logit  (NO sigmoid)
```

**2,765,568 parameters**. There is no sigmoid layer, because training uses `BCEWithLogitsLoss`, which
applies the sigmoid internally in a numerically stable way. (The D in the code also has `Dropout2d(p)` layers
with p = 0 by default; they are identity layers that keep checkpoint keys stable when dropout is switched on.)

### 7b. Conditional DCGAN (the default model)

Labels $y = (\text{view} \in 4,\ \text{hair} \in 9,\ \text{outfit} \in 9)$.

* **Generator $G(z, y)$:** each label → learned 16-d embedding; the three embeddings are concatenated with $z$
  (100 + 48 = 148 inputs) and fed into the same upsampling stack as above. **3,970,272 parameters.**
* **Discriminator $D(x, y)$:** the labels become 22 one-hot "label maps" (4 + 9 + 9 channels, constant across the
  image) concatenated to the RGB input (3 + 22 = 25 channels), followed by the same DCGAN body. D judges
  *"is this a real sprite **with these attributes**?"*, so G is rewarded only when it obeys the labels
  (Mirza & Osindero, 2014). **2,788,096 parameters.**
* During training, the fakes in each batch use the **real batch's labels**, so G sees the true label mix.
* A **projection discriminator** (Miyato & Koyama, 2018; `--d-cond projection`) is also implemented. On this
  small dataset it overpowered G and samples collapsed by epoch 6, so concatenation is the default
  (see the experiment log).
* **EMA:** an exponential moving average of G's weights (decay 0.998) is kept and used for all sampling and for
  `generator_final.pt`.

## 8. Mathematical GAN objective

$$
\min_G \max_D \; V(D,G) = \mathbb{E}_{x\sim p_{data}}[\log D(x)] + \mathbb{E}_{z\sim p_z}[\log(1 - D(G(z)))]
$$

For fixed $G$, the optimal discriminator is $D^*(x) = \frac{p_{data}(x)}{p_{data}(x)+p_g(x)}$; substituting it gives
$V = -\log 4 + 2\,\mathrm{JSD}(p_{data}\,\|\,p_g)$, minimised when $p_g = p_{data}$.

Implemented losses ($\ell$ = discriminator logit):

* $\mathcal{L}_D = \mathrm{BCE}(\ell(x),\, 0.9) + \mathrm{BCE}(\ell(G(z)),\, 0)$ (one-sided label smoothing on real labels)
* $\mathcal{L}_G = \mathrm{BCE}(\ell(G(z)),\, 1)$ (non-saturating generator loss: maximise $\log D(G(z))$)

## 9. Training procedure

For each mini-batch (`train.py`):

1. Load real sprites $x$ (already in [-1, 1]); sample $z \sim \mathcal{N}(0, I)$; compute $G(z)$.
2. **Discriminator step:** $\mathcal{L}_D$ on real and on `G(z).detach()` (detach so no gradient reaches G); Adam step on D.
3. **Generator step:** $\mathcal{L}_G$ through D on the non-detached fakes; Adam step on G.
4. Log `loss_d`, `loss_g`, mean $\sigma(D(x))$, mean $\sigma(D(G(z)))$; **abort with a clear error if a loss is NaN/Inf**.

Per epoch:

* `outputs/training_history.csv` (epoch means, including `sample_diversity`) and `outputs/training_iterations.csv` (every iteration)
* **Mode-collapse detector:** `sample_diversity` = mean per-pixel std across the 64 fixed-noise samples. At
  start-up the same measure is computed on 64 real sprites (≈0.075 on black). If the generated value
  drops below 25% of the real one (after epoch 3), training prints a `WARNING: possible mode collapse`.
* `checkpoints/latest.pt` (overwritten every epoch, atomic write) — a Colab disconnect loses at most one epoch
* `checkpoints/pixelforge_epoch_XXX.pt` every `--checkpoint-every` epochs (default 10; the last `--keep-last 3` are kept)
* `outputs/training_progress/epoch_XXX.png` — 64 **fixed** latent vectors decoded every `--sample-every` epochs (default 5)
* At the end: `checkpoints/generator_final.pt` (generator-only, ~14 MB) and `outputs/plots/losses.png`

**Checkpoint contents** (`latest.pt`, `pixelforge_epoch_XXX.pt`): generator and discriminator `state_dict`s,
both Adam optimizer states, epoch, full config, per-epoch history, history CSV path, fixed noise, parameter
counts and CPU RNG state. Only state dicts and plain Python types are stored (no pickled model objects),
all tensors are moved to the CPU before saving, and loading uses `torch.load(map_location="cpu", weights_only=True)`.
A checkpoint trained on CUDA therefore loads on MPS or CPU, and vice versa.

**Resume** (`--resume` or `--resume auto`, or `--resume PATH`) restores both networks **and both optimizer
states** (Adam moments and step counters are not reset), the history, the fixed noise and the RNG state, then
continues up to `--epochs` (a total, not an increment). Iteration logs written after the checkpoint are truncated.

**Smoke-test mode** (`--smoke-test`): 256-image subset, 2 epochs, batch 32, outputs in
`checkpoints/smoke/` and `outputs/smoke/`. It verifies the whole pipeline in seconds; it does not produce a
usable model.

**Reproducibility:** `seed_everything(42)` seeds Python, NumPy and PyTorch. The DataLoader uses a seeded
generator, and latent vectors for generation are drawn on the CPU from a seeded `torch.Generator`, so
**the same seed gives the same z on CUDA, MPS and CPU**. Two smoke runs on MPS gave identical losses.
(GPU kernels are not bit-exact across devices, so trained weights can differ slightly between CUDA and MPS runs.)

**About transparency:** the GAN outputs **RGB only**. `--transparent` *additionally* writes `*_transparent.png`,

## 17. Evaluation methodology

`python evaluate.py` (or Section 19 of the notebook) writes `outputs/evaluation_metrics.json` and the plots in `outputs/plots/`:

| # | Experiment | Output | What it shows |
|---|---|---|---|
| 1 | Training loss | `losses.png` | G and D loss (separate panels), D(x) and D(G(z)) per epoch |
| 2 | Visual progression | `progression.png` | the same fixed latent vectors after increasing epochs |
| 3 | Real vs generated | `real_vs_generated.png` | 36 labelled real and 36 labelled generated sprites |
| 4 | Latent interpolation | `interpolation_experiment.png` | 3 seed pairs × (linear, slerp); frame-to-frame RMSE |
| 5 | Diversity & memorisation | `diversity.png`, `nearest_neighbors.png` | see below |
| 6 | **Prompt controllability** | `controllability.png`, `prompt_control_grid.png` | does the requested hair / outfit colour appear? |

Experiment 6: for each of the 9 hair colours (and each of the 9 outfit colours), generate 48 sprites that
request it, with the other attributes random. Label them with the *same* automatic labeller used on the training
data, and report how often the requested colour was obtained. The baseline is the same labels compared with
**shuffled** requests, which is what a model that ignores the prompt would score. The labeller's agreement on real
images is reported as an upper bound for the measure. Direction control can't be measured this way (no
direction classifier), so it is shown visually in `prompt_control_grid.png` (columns = back, left, front, right).

Experiment 5 uses 512 generated and 512 real images:

* **Diversity:** mean pairwise per-pixel RMSE within each set; ratio generated/real (≈1 = as varied as real; ≪1 = mode collapse); also on 16×16 average-pooled images (coarse structure), plus near-duplicate pairs.
* **Memorisation:** for each generated image, the RMSE to its nearest image in the **full** training set, compared with the RMSE from real images to their nearest *other* training image. Generated distances far below real ones, or near-zero distances (< 0.02), would indicate copying. `nearest_neighbors.png` shows generated samples next to their 3 nearest training images.
* **Colour statistics:** L1 distance between per-channel colour histograms.
* **Why the loss alone is not enough:** GAN losses measure a moving two-player game. When one network improves, the other's loss goes up even if samples get better, and losses can look stable during mode collapse.
* **Limitations:** pixel RMSE is not perceptual (a 1-pixel shift looks "far"), and 512 samples give noisy estimates.
* **FID is deliberately not computed:** it needs an ImageNet-pretrained Inception network and many thousands of samples, and is unreliable for 64×64 pixel art with ~3.6k training images.

The `interpretation` field in the JSON applies fixed rules to the measured numbers. No result is hard-coded.

## 18. Results and limitations

**Verified in this repository (MacBook Air M2, MPS):**
- All 43 unit tests pass.
- The CLI smoke test runs, as do generation (including `--prompt`), interpolation, GIF export, resume and evaluation.
- The notebook executes top to bottom in a fresh folder (smoke-test mode, since there is no CUDA on a Mac). It downloads TinyHero itself, and its prompt cells work.

**Visual quality:** clear characters with heads, faces in front views, the backs of heads in back views,
narrow side views, and the requested hair and outfit colours (`outputs/plots/prompt_control_grid.png`). They
are cleaner than the plain DCGAN's output, but still noisier than the real sprites.

**Known weakness: little variety within a fully specified prompt.** With view, hair and outfit all fixed,
different z give very similar characters (same-prompt pixel variety ≈ 0.014, vs 0.072 across real sprites;
interpolation endpoints differ by only 0.039 RMSE). This is *conditional mode collapse*: the generator relies
mostly on the labels. A mode-seeking regulariser (MSGAN) increased variety but turned it into noise and
weakened label-following (see the experiment log), so it is not used. Partly specified prompts still give
varied characters, because missing attributes are randomised, and the app says so.

0.89, 0 near-copies, median NN RMSE 0.111 vs 0.088, and noisy but varied characters with no prompt control.

### Experiment log: mode collapse and the background colour

The first full run (white background, standard DCGAN, batch 32) **mode-collapsed**. By epoch 5 all 64
fixed latent vectors decoded to the same sprite, and by epoch 23 the variation across samples was ~6% of
the real data's. D dominated from the first epoch (D(G(z)) ≈ 0.003, loss_G ≈ 6). CPU and MPS gave identical
outputs and gradients (relative difference ~1e-6), and MPS `randn` was correct, so it was not a device
bug. Grids and logs are in `outputs/experiments/01_plain_dcgan_mode_collapse/`.

Controlled 6-epoch probes (seed 42, batch 64, everything else default). "Diversity" is the per-pixel std
across 64 fixed-noise samples, as a percentage of the same measure on 64 real sprites with the same
background (white 0.113, black 0.075):

| Probe (background) | Diversity at epoch 6 | Visual check |
|---|---|---|
| Plain DCGAN (white) | 16% | |
| + instance noise 0.1 (white) | 20% | |
| + D dropout 0.3 (white) | 17% | |
| + instance noise + dropout (white) | 22% | |
| + spectral norm D (white) | 9% | D too weak (D(G(z)) ≈ 0.5, loss_G ≈ ln 2) |
| + spectral norm + noise (white) | 12% | |
| + minibatch std-dev (white) | 16% | collapsed (one sprite) |
| + minibatch std + noise + dropout (white) | 19% | collapsed (one sprite) |
| **Plain DCGAN (black)** | **37%** | **diverse: different colours, heads, bodies** |
| Original TinyHero recipe (black; nz 84, 48 ch, noisy labels, dropout 0.2) | 32% | some variety |

**Conclusion:** the background colour was the deciding factor. With ~76% of every image an exactly uniform
white field, the discriminator separated real from fake almost immediately, and the generator retreated to
one "safe" sprite. Standard stabilisers delayed this but did not prevent it. On black, the plain DCGAN
trains stably, so PixelForge uses black by default and keeps the stabilisers as optional flags.
Per-probe histories and epoch-6 grids are in `outputs/experiments/probes/`. (These are short probes on one
seed: evidence, not proof.)

Limitations:

* Small dataset (912 unique characters); the four views of each character are strongly correlated.
* Unconditional model: no control over direction, class or equipment.
* 64×64 resolution and DCGAN capacity: faces and weapons are often blurry; transposed convolutions can cause checkerboard artifacts.
* GAN training is sensitive to seeds and hyperparameters; mode collapse is possible.
* Evaluation uses simple pixel-space proxies, not perceptual metrics.
* Transparency is not learned (optional heuristic only).

### Experiment log: choosing the conditional discriminator

Same setup (black background, batch 64, seed 42, no EMA), 6-epoch probes. Diversity here is measured across z
with **one fixed label combination**. Histories and epoch-6 grids are in `outputs/experiments/conditional_probes/`.

| Discriminator conditioning | D(G(z)) at epoch 6 | loss_G at epoch 6 | Diversity, epoch 2 → 6 | Visual check |
|---|---|---|---|---|
| Projection, sum-pooled (first attempt, stopped at epoch 6) | ≈ 0.02 | ≈ 6.8 | 0.026 → 0.012 | grey, near-identical blobs |
| Projection, mean-pooled | 0.07 | 6.79 | 0.029 → 0.018 | declining |
| **Concatenated label maps** | **0.19** | **3.54** | **0.021 → 0.026** | **varied; hair rows and side views already distinct** |

The projection discriminator is the stronger design on large datasets, but here it made D dominate and G
collapse, the same failure as in the white-background run. Concatenation keeps the game balanced, so it is the
default (`--d-cond projection` remains available).

### Experiment log: mode-seeking regulariser (MSGAN)

8-epoch probes, concat D, no EMA. "Same-prompt variety" is the pixel std across 32 z, averaged over 8 fixed
label combinations. Grids and histories are in `outputs/experiments/mode_seeking_probes/`.

| MSGAN weight | Same-prompt variety at epoch 8 | D(G(z)) | Visual check |
|---|---|---|---|
| 0 (used) | 0.024 | 0.21 | clean, follows labels, low variety per label |
| 0.1 | 0.055 | 0.21 | blotchy backgrounds, hair labels followed less well |
| 0.3 | 0.057 | 0.20 | noisier |
| 1 | 0.089 | 0.16 | speckle noise, labels largely ignored |
| 5 | 0.212 | 0.01 | noise |

The extra "variety" came mostly from noise, not from different characters, so the final model keeps weight 0.

## 19. Possible improvements

* **More within-prompt variety** — conditional mode collapse could be reduced with more data per label
  combination, diversity-sensitive losses tuned on a larger dataset, or a StyleGAN-style mapping network.
* **Richer labels** — regenerate the dataset with the LPC character generator and keep its metadata (class, weapon, armour), then condition on those, so prompts like "archer with a bow" become possible.
* **A learned text encoder** — with captioned data, replace the keyword parser with a small text encoder trained jointly with the GAN.
* **WGAN-GP or hinge loss + spectral normalisation** — more stable training, less mode collapse.
* **Upsample + convolution** instead of transposed convolutions — removes checkerboard artifacts.
* **Generate RGBA directly** — a 4th output channel for learned transparency.
* **Data augmentation / DiffAugment** — helps GANs on small datasets.
* **EMA of generator weights** — smoother, higher-quality samples.
* **Perceptual metrics** — KID (better than FID for small sample sizes) or LPIPS diversity.
* **StyleGAN-style mapping network** — more disentangled latent directions for controllable edits.

## 20. Troubleshooting

| Problem | Fix |
|---|---|
| **"CUDA requested but not available" / no CUDA on Mac** | Expected: Macs have no NVIDIA GPU. Use the default `--device auto` (picks MPS) or `--device mps`. Do not install CUDA PyTorch wheels on macOS. |
| **MPS unavailable** (`torch.backends.mps.is_available()` is False) | Needs Apple Silicon, macOS ≥ 12.3 and an arm64 Python (`python -c "import platform; print(platform.machine())"` must print `arm64`, not `x86_64`/Rosetta). Reinstall: `pip install --upgrade torch`. Training still works on CPU (~50 min for 50 epochs). |
| **MPS op not implemented** | `export PYTORCH_ENABLE_MPS_FALLBACK=1` before running, or use `--device cpu`. |
| **Colab GPU unavailable** ("cannot connect to GPU backend" / usage limits) | The notebook switches to smoke-test mode automatically. Try again later, or train locally on MPS (`python train.py --epochs 50 --batch-size 32`, ~12 min on M2). |
| **Out of memory** | Lower `--batch-size` (32 or 16). On Colab, *Runtime → Restart session*. Memory use is small (~1–1.5 GB at batch 64). |
| **Disk full during `torch.save`** (`RuntimeError: ... unexpected pos ...`) | Free disk space. `latest.pt` needs ~76 MB plus a temporary copy; use `--keep-last 1`. |
| **Prompt Studio says the checkpoint is unconditional** | The selected file was trained with `--unconditional` (or before prompts existed, e.g. `checkpoints/unconditional/`). Pick `generator_final.pt` in the sidebar, or retrain with `python train.py --epochs 100`. |
| **Prompt ignores some words** | Only direction, 9 hair colours and 9 outfit colours are understood (see the chips under the prompt box). Use the "Adjust attributes manually" panel to override. |
| **Missing checkpoint** ("No checkpoint found") | Train first, or unzip `pixelforge_results.zip` into the project folder so `checkpoints/generator_final.pt` exists, or pass `--checkpoint PATH`. In Streamlit, upload a `.pt` from the sidebar. |
| **`--resume` says generator-only file** | Resume needs a full checkpoint (`latest.pt` or `pixelforge_epoch_XXX.pt`), not `generator_final.pt`. |
| **Dataset extraction errors** ("not a valid zip archive") | Delete `data/data.zip` and `data/tinyhero/`, then run `python dataset.py --force-download`. If GitHub is blocked, run `git clone https://github.com/AgaMiko/pixel_character_generator`, copy its `data.zip` into `data/`, then run `python dataset.py`. |
| **Dependency installation errors** | Use Python 3.10–3.12 in a fresh venv: `python3.11 -m venv .venv && source .venv/bin/activate && pip install --upgrade pip && pip install -r requirements.txt`. On Colab, everything except Streamlit is preinstalled (the notebook does not need Streamlit). |
| **`ModuleNotFoundError: _lzma`** (pyenv Python) | Your Python was built without xz. PixelForge does not need torchvision (which triggers this), so it is not in `requirements.txt`. If you need it: `brew install xz` and then `pyenv install 3.11.9` again. |
| **Streamlit shows old results** | Press *R* in the browser, or restart `streamlit run app.py`. Cached models refresh when the checkpoint file changes. |

To rebuild the notebook after editing any module: `python tools/build_notebook.py`.
